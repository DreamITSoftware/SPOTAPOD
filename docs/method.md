# Method

## De-identification approach

Every script in this repo follows the same rule: author/profile identifiers
(`AuthorPublicIdentifier`, `public_identifier`, `name`, `linkedin_profile_id`,
`linkedin_profile_link`, `profile_picture`) are read once, passed through
`hashlib.sha256`, and used only as dictionary keys for counting. The hash is
never written to disk, never printed, and cannot be reversed to the original
identifier from anything this repo outputs. This means the repo can report
"7,033 unique authors" or "the top 1% of authors account for 19.1% of posts"
without ever being able to tell you, or anyone else, *which* authors those are.

Post `Content` and `post_title` text is aggregated only at the level of exact
duplicate counts (e.g., how many times a given string appears, how many
authors a given cluster spans) — never joined back to a specific record's
author in any printed output.

## Post-date decoding (podawaa2024)

`linkedinPostId` values are LinkedIn share/activity URNs, which follow a
Snowflake-style bit layout. Shifting the ID right by 22 bits yields
milliseconds since the Unix epoch directly (LinkedIn does not add the extra
custom epoch offset that Twitter's original Snowflake scheme used). This was
verified empirically against several IDs in the dataset whose decoded dates
land in the expected 2018–2024 range; it is an **INFERENCE** about the ID
encoding, not something confirmed by LinkedIn documentation, so treat decoded
years as approximate.

## Reciprocal engagement flags (HyperClapper)

The `like` and `comment` booleans in the HyperClapper export appear to record
whether the pod tool successfully executed a reciprocal like and/or comment
action on a given post — not whether the *post's author* liked or commented
on anything. That distinction matters: a record with `like=true,
comment=true` is a **STATED** signal that a reciprocal action tied to this
post happened via the tool, not independent confirmation of it, and it is
not by itself evidence of the scienter or commercial-purpose elements that
[16 CFR § 465.8](regulatory-context.md) actually requires.

## Target-post and operator concentration (LinkBoost-2025)

`ObjectUrn` and `UserId` are hashed the same way as author identifiers in
the other two files — one-way SHA-256, in-memory only, used solely to count
records per hashed value. "Target-post concentration" measures how
unevenly the 77,969 records are spread across the 469 distinct `ObjectUrn`
values; "operator concentration" does the same across the 238 distinct
`UserId` values. Neither figure identifies which target or which operator
sits at any point on the curve.

## Ratio and completeness figures

Likes/Views and like_count/impression_count ratios are computed only over
records with a non-zero denominator, and that exclusion is reported explicitly
(see the "zero views" / "zero impressions" figures) rather than silently
dropped, so the ratio figures aren't read as covering the whole dataset.

## Reproducibility

Every number in [docs/baseline-profile.md](baseline-profile.md) and every
chart in [figures/](../figures) is generated by a script in [analysis/](../analysis)
or [figures/generate_figures.py](../figures/generate_figures.py) that takes only
a file path as input — no manual editing of intermediate output.
